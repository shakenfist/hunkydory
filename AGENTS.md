# AGENTS.md

Guidance for agents working in this repository. See
[ARCHITECTURE.md](ARCHITECTURE.md) for how the code fits together and
[docs/](docs/) for detail.

## Conventions

- `src/diff.ts` and `src/recount.ts` must never import `vscode`. That is what
  lets the test suite run under plain node. Anything needing the editor API
  goes in `src/extension.ts`.
- New validation in `tools/build-vsix.sh` and `tools/publish-marketplace.sh`
  goes in the **host** stage wherever it can. Each file is two programs, and
  only the host half runs without a docker daemon, which is what
  `test/scripts.test.ts` can reach. A check that needs node has to wait for
  the container; everything else fails faster and gets a test if it goes
  before the `docker run`.
- Wrap at 100 characters. Two-space indent, single quotes, semicolons.
- TypeScript runs with `strict`, `noUnusedLocals` and `noImplicitReturns`. Do
  not loosen these to make something compile.
- `REVIEWS.md` and everything under `.vscode/` except `review-scope.toml` is
  generated by `tools/review-tracking.sh` and attests to human review. Never
  edit them by hand or mark a file reviewed yourself.
- Changes merge to `develop` through the merge queue, never around it: a
  release tag is only accepted on a commit whose queue run passed. The one
  exception is prune-reviews' review-state commits, which shakenfist-bot
  pushes directly and the release gate steps across. A new `ci.yml` job
  goes in the `needs:` of "Can enqueue" and "Can merge". See
  [docs/development.md](docs/development.md).
- `.github/exported-config/` is written by the repository management tooling
  that exports GitHub settings across every repository it manages, so its
  formatting is not this project's to set. `biome.json` points Biome away from
  it. Do not reformat it or drop the exemption. The exemption cannot carry a
  comment explaining itself in place: Biome rejects comments in a `.json`
  config and then falls back to its *defaults*, which silently lints `out/`
  and `node_modules/` as well.

## What to run before committing

[docs/testing.md](docs/testing.md) has the test layers, what each checks and
how to replay a fuzzer failure. What a change owes them:

- `npm test` and `npm run corpus` must pass before a commit.
  `pre-commit run --all-files` covers `npm test` (via `tools/check-node.sh`,
  which also runs the build and Biome) but not the corpus, whose external half
  depends on a sibling checkout -- run that by hand.
- If you change counting behaviour, `npm run fuzz` must come back clean, and
  the corpus must be run against a real patch set, not just the fixtures. It
  is easy to under-value: most of the edge cases in `diff.ts` were found that
  way rather than by reasoning.
- Do not add a fixture to `test/fixtures/` that turns on either ambiguity in
  [docs/ambiguity.md](docs/ambiguity.md); `test/corpus.ts` explains why.
- If you touch how `extension.ts` reads a document or applies edits, run
  `tools/editor-test.sh` yourself rather than waiting for CI.
- If you touch `.vscodeignore` or add a module under `src/`, run
  `tools/check-package-contents.sh`: what ships is decided by vsce's matcher,
  and no test can reach it.

Before pushing a pull request, work through [PUSH-AUDIT.md](PUSH-AUDIT.md),
the pre-push review runbook.

## The thing that will catch you out

Counting a hunk body is not simply "lines starting with - or +". The rules that
are easy to miss, each of which broke a real patch:

- git's `-- ` signature before the version trailer starts with `-` but is not a
  deletion.
- A deleted `-- comment` is the body line `--- comment`. Where files start with
  `diff --git`, a `--- ` in a hunk is always body; bare `diff -u` is harder.
- A bare empty line is a context line that lost its leading space.
- `\ No newline at end of file` counts on neither side.
- A count of exactly 1 is elided: `-1,1` is written `-1`.
- An empty range names the line before it: creation is `-0,0 +1,N`, deletion
  `-1,N +0,0`, and a `-U0` insertion after line 3 `-3,0 +4,2`.
- Two cases are genuinely ambiguous. Read [docs/ambiguity.md](docs/ambiguity.md)
  before touching `resolveCounts` or `startsFile`.
- Lines reach the rules with their terminators already removed. Split a patch
  string with `splitPatch`, never `split('\n')`: the leftover CR of a CRLF
  file is content as far as the rules are concerned, and reading it as such
  made every CRLF patch a silent no-op for four pull requests. The same goes
  for an editor document: `lineAt(0..lineCount)` ends with a phantom empty
  line after the final newline, which corrupted the last hunk of a file.

A header that is too large makes git reject a patch loudly. One that is too
small makes git *silently truncate the hunk* and apply the wrong content. When
in doubt, over-count.
